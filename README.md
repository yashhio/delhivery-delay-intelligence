# Delhivery Last-Mile Delay Intelligence Pipeline

A reproducible, end-to-end capstone pipeline using **synthetic** shipment data. It cleans the raw exports, estimates delivery hours, classifies likely delays, segments hubs into operational playbooks, and scores 48 not-yet-dispatched parcels. The data does not contain real Delhivery shipment records.

## How to run

Run these commands from the repository root, in this order, after cloning the repository:

```bash
pip install -r requirements.txt
python generate_data.py
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

`generate_data.py` regenerates the three raw data files. The pipeline writes the modelling table, CSV checks, evaluation results, hub segments, model artefacts and final actions under `data/`, `outputs/` and `models/`. `models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only with the scikit-learn version pinned in `requirements.txt`; if installed versions differ, regenerate it with `package_model.py` rather than relying on the committed pickle. Scripts are designed to run from the repository root and use only repository files.

## Data findings

- **Express parcels have the highest delay rate:** 119 of 243 shipments were delayed, a rate of **0.4897**. Standard was 0.2056 and Economy was 0.0857 (`outputs/part_a_delay_by_group.csv`).
- **Delay rate rises sharply across hub tiers:** Tier 1 was **0.0400**, Tier 2 was **0.2150**, and Tier 3 was **0.4400** (`outputs/part_a_delay_by_group.csv`).
- **Longer distance bands have higher delay rates:** 0–200 km was **0.0219**, 201–400 km was **0.1368**, 401–600 km was **0.4364**, and 601+ km was **0.8523** (`outputs/part_a_delay_by_group.csv`).
- The three largest absolute correlations with `delivery_hours`, excluding the target itself, were `promised_hours` (**+0.8372**), `distance_km` (**+0.4013**) and `n_stops` (**+0.3247**) (`outputs/part_a_correlations.csv`). These are associations, not proof of causation.
- `declared_value_inr` is right-skewed: its median-filled mean was **INR 1,533.0542** and its median was **INR 1,121.5000**, while the natural-log mean and median were **7.0277** and **7.0224** (`outputs/part_a_checks.csv`). The log transform compresses the long upper tail and makes the scale less dominated by high declared values.
- The raw export contained **1,224** rows; removing **24** exact duplicates left **1,200** unique shipments. The cleaned modelling features and target had **0** missing cells (`outputs/part_a_checks.csv`).

## Model results (regression)

The validation baseline predicts the training-target mean for every validation parcel. Its R² was **−0.0212**, meaning it performed slightly worse than predicting the validation mean and did not explain useful variation.

**Linear regression won on validation**, with RMSE **4.8912 hours** and R² **0.9313**. Gradient boosting was close at RMSE **4.9165 hours** and R² **0.9306**; the decision tree's best depth was **6**, with validation RMSE **6.2796 hours**. The depth-1 tree has high bias because train and validation RMSE are both high (**11.6334** and **12.1324**). The unlimited tree has high variance: train RMSE is **0.0000** but validation RMSE is **7.8368**, a large generalisation gap.

For gradient boosting, learning rate **0.1** performed best (validation R² **0.9306**). At **0.01**, R² was **0.7127**, consistent with learning too slowly with 100 estimators; at **1.0**, R² was **0.8440**, consistent with overly aggressive updates that overshoot a useful fit. Cross-validation on the training-plus-validation rows gave mean R² **0.9261** for linear regression and **0.9353** for gradient boosting. Since validation RMSE selected linear regression and the cross-validation scores are close, the chosen model is linear regression, supported by its strong held-out test R² of **0.9493** and test RMSE of **4.5235 hours** (`outputs/part_b_metrics.csv`, `outputs/part_b_cv.csv`).

## Model results (classification)

The blind baseline's validation accuracy was **0.7667**, but its confusion matrix was TN **138**, FP **0**, FN **42**, TP **0**: it misses every delayed parcel, so the accuracy is misleading for operations.

The five bookkeeping/noise columns together contributed **0.2245** of the 17-column forest's importance. All five were outside the top seven by F-score; the top seven were `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag` and `sale_event_flag` (`outputs/part_c_feature_scores.csv`). The feature-selection experiment supports **k = 7**: validation F1 was **0.8333** for k=7, versus **0.6988** for k=5, **0.7857** for k=10, **0.8049** for k=12 and **0.7848** for k=17 (`outputs/part_c_selectk.csv`).

Tuning did **not** beat the untuned forest on the 180-row validation set: the default forest on the same seven selected features reached F1 **0.8333**, compared with **0.7750** for grid search and **0.7848** for randomized search. This illustrates why choosing hyperparameters from a small validation set can be noisy; cross-validation accuracy alone did not translate into a better validation F1. The selected configuration is the default 100-tree forest with seven selected features (`outputs/part_c_tuning.csv`, `outputs/part_c_final_config.csv`).

The operations rule selects the **highest threshold with validation recall at least 0.80**, which is **0.5**. At that threshold, validation precision was **0.7955** and recall was **0.8333**: a higher threshold would reduce unnecessary calls but miss more delays. On the test set, precision was **0.6889**, recall **0.7561** and F1 **0.7209** (`outputs/part_c_final_test.csv`). Test recall was lower than validation recall; the test contains only **41** delayed parcels, so a few outcomes materially change the estimate.

## Operations recommendation

The **Escalate** segment contains nine hubs: **HUB13, HUB15, HUB17, HUB18, HUB19, HUB20, HUB21, HUB23 and HUB24**. Its hub-average delay rate is **0.4600**; mean delivery time is **64.6504 hours** (`outputs/segment_profile.csv`). Give these hubs the hub-manager escalation playbook, with attention to route distance and stop counts.

Four hubs do not behave like their tier label implies:

- **HUB07, Kolkata:** Tier 1 but `Watch`; do not assume it behaves like the other Tier 1 hubs.
- **HUB13, Nagpur:** Tier 2 but `Escalate`; apply the escalation playbook.
- **HUB15, Kochi:** Tier 2 but `Escalate`; apply the escalation playbook.
- **HUB22, Dehradun:** Tier 3 but `Watch`; use its observed segment rather than escalating solely because of its tier.

The alert threshold is **0.5**. Test precision **0.6889** means about **6.9 of every 10 flagged parcels** were actually delayed; test recall **0.7561** means about **7.6 of every 10 delayed parcels** were caught (`outputs/part_c_final_test.csv`). For the 48 new parcels, **8 were flagged** and **6 of those** require hub-manager escalation; the other flagged parcels receive a proactive customer call (`outputs/new_shipment_actions.csv`).

We keep **K = 3** because operations has exactly three playbooks, and the K=3 solution has usable segment sizes of **9–8–7** hubs with an across-to-within distance ratio of **5.3928**. The ratio rises to **6.3047** for K=4 and **6.8866** for K=5, but those solutions include a cluster smaller than six hubs, too small to justify a separate operational playbook (`outputs/part_d_separation.csv`).

## Production plan

- **Accuracy:** track precision, recall and F1 on parcels whose outcomes are known; the held-out test results are recorded in `outputs/part_c_final_test.csv`.
- **Reliability:** `package_model.py` reloads the saved model and checks probability parity; `outputs/part_d_reload_check.csv` records **180** scored test rows and a maximum absolute probability difference of **0.0**.
- **Reproducibility:** `generate_data.py` fixes the synthetic data seeds, scripts use the specified split and model seeds, and CSV outputs are written without index columns.
- **Performance:** benchmark `predict_delay.py` on each 48-parcel batch and alert if p95 scoring time exceeds **2 seconds** on the deployment machine.
- **Maintainability:** shared constants and reusable cleaning/feature functions live in `src/shipment_prep.py`, rather than being copied into the prediction script.
- **Consistency:** training and inference use the same `clean_shipments` and `build_features` functions; the inference path loads the persisted medians and exact feature order.
- **Monitorability:** log probabilities, flags, action, hub, segment, dispatch date and eventual outcome for audit and threshold evaluation.

Suggested monitoring triggers (review and investigate when any trigger is breached):

1. **Delivered-parcel delay share:** alert if the rolling 7-day share exceeds **30%**, excluding parcels whose outcomes are not yet known.
2. **Flag rate:** alert if more than **35%** of dispatched parcels are flagged in a rolling 7-day window, or if the rate changes by more than **10 percentage points** from its trailing 8-week baseline.
3. **Recall after outcomes mature:** alert if the rolling 4-week recall falls below **0.75** once at least **40 delayed parcels** have known outcomes.
4. **Feature drift:** review if the population stability index (PSI) for `distance_km` or `n_stops` exceeds **0.20** against the training reference distribution.

Retrain monthly after labels mature, with an additional review after a major operational change. The generator includes a sale window from **15–28 September** (`sale_event_flag`); compare sale-period performance with other sale periods, not ordinary weeks. Drift could appear as a sustained shift in route distances, stop counts, service mix, rain/sale incidence, hub delay rates, or the model's probability/flag distribution. Recalibrate the threshold only after evaluation on a separate, time-ordered validation window.

## Limitations

1. **Synthetic data:** the generated relationships are simpler and cleaner than real logistics operations; these results are not evidence of real Delhivery performance.
2. **Small test sample:** the test split has only **180** parcels and **41** delayed outcomes, so precision and recall have uncertainty.
3. **Single split and threshold:** the alert threshold was chosen from one validation split; production performance may differ and should be checked on later, time-ordered data.
4. **No causal interpretation:** correlations and hub segments describe patterns in this dataset and do not prove that changing a feature will cause delays to fall.
5. **Limited operational context:** the synthetic records omit traffic, handover scans, holidays beyond the generated sale flag, rider availability and live weather severity.
